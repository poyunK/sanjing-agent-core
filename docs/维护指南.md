# 维护指南

这份指南按工程中的真实边界来说明怎样增加能力。工具实现放在 `sanjing.tools`，工具描述和执行都要显式登记；持久化由 `sanjing.store` 负责；匹配规则由相应业务函数管理并带版本号。

## 增加一个只读工具

先确定这个工具只需读取什么、会不会跨会话访问数据、输入最多多长。然后：

1. 在 `sanjing.tools` 中写一个小函数，参数明确，返回普通字典。
2. 在 `_TOOL_SPECS` 注册表中登记同名工具、参数格式、权限类别和处理函数；`tool_definitions()` 与 `execute_tool(ctx, call)` 都从这里读取。
3. 统一执行入口会依次调用 `sanjing.safety.parse_arguments(...)`、`check_tool_permission(...)` 和 `validate_schema(...)`。新工具沿用这条路径，不要从主循环直接调用处理函数。
4. 如果返回内容会成为建议依据，在处理函数中用 `_save_evidence(ctx, kind, data)` 保存内容和来源，并返回证据编号；统一入口负责执行事件。
5. 加一个离线测试：正常参数能够读取，错误参数与跨会话 ID 被拒绝，拒绝前没有调用业务函数。

不要把模型给的路径、SQL、命令或任意 URL 传给通用执行函数。当前能力白名单是应用层保护，不是操作系统沙箱。

### 跟着增加一个「说明演示限制」工具

下面是扩展练习，本工程没有预先注册它。先在 `tools.py`、`_TOOL_SPECS` 定义之前增加这个函数。它读取程序内的固定说明，通过现有 `_save_evidence` 自动保存来源：

```python
def _get_demo_notice(ctx, args):
    data = {
        "quote": "本工程使用合成测评与团队原型规则，不能代表真实职业适配结论。",
        "source": "工程维护者的演示说明",
        "demo": True,
    }
    evidence_id = _save_evidence(ctx, "demo_notice", data)
    return {"data": data, "evidence_ids": [evidence_id]}
```

然后在同一个 `_TOOL_SPECS` 字典中增加一项，注意逗号和缩进：

```python
"get_demo_notice": {
    "description": "读取原型演示的限制说明，并保存来源。",
    "parameters": _object_schema({}, []),
    "permission": "business_read",
    "handler": _get_demo_notice,
},
```

不需要改主循环：`tool_definitions()` 会把这一项转换为 API 工具描述，`execute_tool()` 会从同一项找到处理函数。普通的业务只读工具仍会保存执行事件与证据，不能因此理解为完全没有数据库写入。

先用离线测试直接调用统一入口：在 `test_integration.py` 增加下面的测试方法，复用该文件已有的 `self.ctx()` 和 `self.call()`：

```python
def test_demo_notice_extension(self):
    ctx = self.ctx()
    result = self.call(ctx, "get_demo_notice", {})
    self.assertTrue(result["ok"])
    evidence_id = result["evidence_ids"][0]
    record = store.get_evidence(self.db, self.session, evidence_id)
    self.assertEqual(record["kind"], "demo_notice")
    rejected = self.call(ctx, "get_demo_notice", {"path": "任意路径"})
    self.assertFalse(rejected["ok"])
```

通过测试后，已经可以在测试中确认函数、事件和依据的连接。这里无需调用真实 API。新增工具也不会自动改变 `offline.ask_offline` 的固定脚本，所以普通离线提问不会自行选择它；需要时再学习修改模拟响应。

这个工具只提供说明，没有完成发布流程。因此单独要求它解释限制，真实模型最后如果只返回普通文字，会被当前主循环拦截；不要把这种现象误判为新增工具没有执行。可以查看工具事件与候选证据，判断函数是否成功。完成后你应该能回答：模型描述、Python 函数、权限和证据 ID 分别在哪里产生。

## 增加岗位资料

演示岗位资料放在工具当前读取的本地数据结构中。每条资料应带稳定 ID、标题、原文片段、来源名称或位置，以及“演示资料/已审核/待审核”等状态。检索结果只是候选材料；生成建议时明确哪些 ID 被实际采用。页面会以纯文本显示原文，特殊 HTML 字符会转义。

关键词检索是便于教学的确定性示例，不是向量检索。以后替换为向量库时，保留同一层工具返回结构，并继续返回原文片段、来源和稳定 ID。

## 修改匹配规则

修改权重或公式时提升规则版本，并记录本轮实际输入、每项贡献、缺失信息与规则状态。演示权重标为团队假设。不要把向量相似度、规则分数或模型自评置信度叫作录用概率或职业适配概率。

旧建议保留旧轮次快照；不要在查看历史页面时用新规则重新计算并覆盖旧结果。引用检查只能确认记录关系，支持性仍需人工审阅。

## 改主循环或上下文

从 `sanjing.agent.run_turn` 读起：先理解模型请求次数、工具调用循环、完成状态，再读 `sanjing.context` 的回合裁剪。消息中助手工具调用与工具结果必须保持相邻逻辑关系，并用 `tool_call_id` 配对。不要只截取列表尾部而把一组工具调用和回执拆散。

保存长期历史与发送给模型的本轮上下文是两件事。需要缩短上下文时，先裁剪完整旧回合；结构化测评结果和规则版本仍从存储读取，不依赖聊天摘要。

## 检查与排错

在 `agent_core` 目录运行：

```powershell
python -m unittest discover -s tests -v
```

单独检查静态账本页面可以运行 `python -m unittest discover -s tests -p test_viewer.py -v`。先使用模拟模型和合成数据。真实 API 测试会发送数据并消耗额度，必须保持测试输入为合成内容。

排错按层找：模型请求失败看 `model` 的状态与错误代码；工具拒绝看参数校验和执行事件；页面缺少依据看 `store.snapshot` 与建议记录的证据 ID；任务未完成先确认循环次数上限，而不是把失败回复当最终结果。
