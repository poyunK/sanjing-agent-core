# 专业数据是怎样进入 Agent 的

这篇是给你回来后亲自阅读的工程教材。建议先运行 `start.bat` 选项 5，然后跟着一条真实函数调用往下读。离线演示使用合成资料，不读取 Key，也不访问网络；真实模式使用同一套工具分发和账本。

## 先理解三个函数分别负责什么

`agent.run_turn()` 管一轮对话。它保存用户输入，准备 `messages`，请求模型，处理模型提出的工具调用，最后展示通过校验的建议。

`datapro.query_data()` 管一次网络查询。它读取工程外的 DataPro Key，与固定的 MCP 服务通信，返回一个字典。它不写数据库，也不能执行返回资料中的命令。

`tools.execute_tool()` 管工具执行。它先查注册表、检查参数和权限，再调用业务函数，并记录执行事件。模型不会拿到 Python 函数对象，它只能提出工具名称和参数。

这三个职责分开以后，你可以更换查询服务，而不必重写主循环；也可以模拟网络返回，而继续使用真实的存储和安全检查。

## 一条查询的数据旅行

用户在终端说“比较两家公司的登记资料”。这句话首先变成 `run_turn()` 的 `user_text`，并保存为用户输入证据。程序准备的 `messages` 是一个列表，每个元素都是一条带 `role` 和 `content` 的字典。

模型可能在回复中提出下面的工具参数。它此时还没有真正执行函数：

```json
{"category": "company_profile", "query": "比较合成企业甲与合成企业乙的登记资料。"}
```

主循环把完整的 assistant 工具调用消息加入列表，再把这次调用交给 `execute_tool()`。注册表将名称 `query_professional_data` 对应到 `_query_professional_data()`。如果模型提出未注册的 `run_shell`，程序在分发前就会拒绝。

业务函数给查询添加类别提示，检查本轮预算与缓存，再调用 `ctx["data_client"]`。真实模式里，它最终进入 `datapro.query_data()`；离线练习里，它进入 `professional_demo.demo_data_client()`。

同一轮中相同类别、相同文字的查询复用成功结果，也复用已发生的错误，避免模型重复提出失败查询而再次进入付费客户端。下一轮会使用新的缓存；查询文字确实需要调整时才产生新尝试。

离线返回的字典中有 `code`、`dataset_type` 和 `items`。`items` 是候选记录列表，每条记录又是字典。这里的“字典套列表再套字典”与模型接口的结构相似，但用途是保存专业资料。

```json
{"code": 0, "dataset_type": "company_profile", "items": [{"name": "合成企业甲", "status": "存续（合成）"}]}
```

业务函数检查返回是否有效。通过后保存查询快照，并为每条候选资料建立证据 ID。给模型的返回只是有长度上限的索引，不会把整份工商资料或几十篇摘要都追加到消息列表。

主循环随后追加 `role: "tool"` 的结果消息。它的 `tool_call_id` 必须等于模型刚才提出的调用 ID。只有这样，下一次请求模型时，它才知道这份结果属于哪次查询。`--trace` 会显示这组配对，但不显示 Key。

## 字段路径是什么

`get_record()` 让模型按证据 ID 读取详细资料。查询索引只表示“找到这个候选”，不能直接引用还没读过的字段。程序会记录本轮实际回传的字段范围；未读取就提交，会得到 `field_not_read`，模型需要先补读再提交。

`field_path` 用来定位这条证据里面的一个字段。例如：

```text
/record/name
/record/企业状态
/record/year
```

`/record/name` 的意思是：从证据的 `data` 字典进入 `record`，再取出 `name`。这不是文件路径，也不能用它读取硬盘。程序只在已保存的字典或列表里逐层查找。

专业资料记录保存的是 `record`；用户原话保存的是 `quote`，因此用户自述引用使用 `/quote`。字段不存在、引用属于另一个会话，或资料没有成功执行来源时，提交会失败。

## 为什么不能让模型把查询结果重新抄一遍

如果原始记录里的成立日期是某个日期，模型重新抄写可能写错。`submit_decision()` 因此接收引用位置，由程序取出真实值并保存到 `resolved`。

事实标签与用户原话标签也由程序生成。模型不能用一个真实的“公司名称”字段，给事实区起名为“公司必然增长”。模型的定性分析放在 `inference` 中，并明确显示“模型生成”。

```json
{"kind": "fact", "text": "资料字段", "citations": [{"evidence_id": "这里填写实际返回的ID", "field_path": "/record/name"}]}
```

这段示意中的 ID 不能直接运行；练习时要使用当前工具返回的真实 ID。它展示的是实际提交接口的参数结构，没有另造一套教学实现。

记录有引用关系，只能证明程序保存了这组关系。研究摘要是否真的支持某项职业判断，仍要看原文、研究方法和适用人群。程序不会因为论文命中就改变演示岗位的权重。

## 怎样理解不完整的资料

查询失败或超时不会生成可引用的成功资料。超时表示本地停止等待，不表示供应商取消了请求或免除了费用；程序不会自动重试。

查询成功也可能缺少原始来源链接、发布时间、单位或数据类型。这些缺失会进入账本限制。没有风险记录，应表述为“本次没有找到相关记录”；企业登记正常，也不能推出岗位适合某个人。

模型可以读取更多候选、解决歧义或补查指标，但每轮最多十六次专业请求、八次模型请求、三百秒。完全相同的本轮查询会复用结果，不再发外部请求。

历史账本保存生成时的输入与来源。用户更新城市条件时，`record_condition()` 可以显式引用 `supersedes_evidence_id`；旧原话仍在库中，待确认提取不会立即取消旧条件。`context.effective_conditions()` 负责整理当前条件。

## 先预测，再运行

先预测：运行下面的命令，会有几次模型选择工具？资料是否来自网络？

```powershell
python -m sanjing.cli --professional-demo --trace --once "比较合成企业资料"
```

答案：确定性演示依次选择查询、读取记录、提交决策，通常是三次模拟模型调用；企业演示会请求两个模拟数据查询。模拟查询仍经过真实工具入口、SQLite 和 HTML 生成，但没有付费网络请求。

再观察：打开返回的“为什么”页面，找到事实字段与模型分析。确认它们共用证据 ID，但显示标签不同。展开执行记录，查看查询次数、状态和耗时。

最后改一处：复制 `demo_data_client()` 使用的合成资料，在其中新增一个只读字段；让你的模拟模型引用该字段，而不是让模型自己写它的值。参考维护指南添加自己的只读工具后，运行离线测试。不要修改真实公司的资料来完成这个练习。

## 阅读顺序

先看 `professional_demo.ask_professional_demo()`：它怎样读取之前的 tool 结果并选择下一步。接着看 `agent.run_turn()` 的工具循环，再看 `tools._query_professional_data()` 和 `tools._submit_decision()`。最后才看网络客户端里的 MCP 细节。

客户端的初始化、会话头和 SSE 是网络协议细节，业务工具只需接收一个查询字符串、得到一个资料字典。你理解了参数从哪里来、返回值交给谁，就能先维护业务层；不必一次读懂所有网络代码。
