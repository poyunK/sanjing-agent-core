# 代码阅读路线

这份路线把教材《从 Python 到你的第一个 Agent》的例子对应到本工程。先读结构，再沿一条任务追踪；不要一开始同时打开所有模块。

如果是第一次读工程，先看 [从教材到工程](先读这篇_从教材到工程.md)。本页是定位函数的索引，不要求一次全部读懂。

## 1. 从教材概念找到工程入口

教材第 1 章的 `message` 是描述一条消息的字典，`messages` 是按顺序保存消息的列表。本工程在 `sanjing.context` 里组装同一种数据：`role` 表示是谁说的，`content` 是消息正文；工具调用和工具结果也要保持原有顺序。

从 `sanjing.cli` 开始看命令行怎样读取用户输入，再进入 `sanjing.agent.run_turn(session_id, user_text, ...)`。`run_turn` 是之后网页层可以调用的入口：传入会话 ID 和文本，拿回状态、回答、轮次 ID 和账本路径。

## 2. 顺着一次 ReAct 循环读

教材第 9 章的核心函数叫 `run_agent(question, max_steps=5)`。它每次先请求模型，把模型消息加进 `messages`；有工具调用时逐个执行，把每个结果作为 `role="tool"` 消息并带回对应的 `tool_call_id`；然后再次请求模型。工程里同一过程由 `sanjing.agent.run_turn` 负责，真实请求由 `sanjing.model` 执行，离线确定性响应由 `sanjing.offline` 提供。

调用链可以按下面顺序读：

1. `cli` 取得一条用户输入。
2. `agent.run_turn` 建立本轮状态并向 `context` 要求消息列表。
3. `model` 返回助手消息；若含工具调用，主循环交给 `tools.execute_tool(ctx, call)`。
4. 工具结果用相同的调用 ID 加回消息列表，主循环继续。
5. `store` 保存用户消息、工具事件、依据和最终建议。
6. `viewer.write_snapshot(...)` 读取某一轮快照，生成静态“为什么”页面。

## 3. 读懂工具注册与拦截

教材第 6 章把函数放进 `tools = {"add": add}` 字典，再从字典中找函数。本工程在 `sanjing.tools.tool_definitions()` 提供模型可见的工具说明，在 `sanjing.tools.execute_tool(ctx, call)` 按固定名字分发。这个表就是模型能力的白名单。

工具执行前，`sanjing.safety.parse_arguments(...)` 解析参数，`check_tool_permission(...)` 检查权限，`validate_schema(...)` 校验字段和类型。未知名称或参数错误会成为结构化失败结果，并写进执行事件；错误消息仍按 `tool_call_id` 回给模型。这样模型可以修正请求，但失败记录不会被当成成功证据。

## 4. 理解账本不是“思维链”

账本保存的是可核查的业务记录：输入、检索到的资料、实际计算、规则版本、限制和建议。这些内容由 `tools` 与 `store` 产生并连接。`viewer` 只读取结构化快照，没有模型内部推理文本可展示，也不会尝试恢复它。

页面上有证据 ID，只能证明引用关联存在；资料是否支持规则，还要人工核对。演示规则应保留“团队假设、待验证”的标记。模型可以帮忙把记录讲得通顺，不能替代规则验证。

## 5. 三个阅读时要停下来想的问题

- `messages.append(...)` 是在修改原列表；`append` 的返回值是 `None`。教材第 2 章展示这个区别，本工程也依赖消息列表按顺序累积。
- 工具调用和工具结果用 ID 配对。看到 `role="tool"` 的 `tool_call_id` 时，往前找助手 `tool_calls` 中相同的 `id`；不要把工具结果伪装成用户消息。
- `status="incomplete"` 表示整轮未完成。某次工具失败可以回传给模型并修正，不一定使整轮失败；流畅的文字也不能替代建议引用检查。
