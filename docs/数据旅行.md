# 一条请求的数据旅行

这份说明用于回顾一次用户请求如何经过各层。第一次学习请先读 [从教材到工程](先读这篇_从教材到工程.md)，再按需打开对应函数，不必同时打开四个模块。

## 1. 用户文本进入消息列表

命令行把用户文字和会话 ID 传给 `run_turn(session_id, user_text, ...)`。`context` 从数据库取最近的完整对话回合，并加入本轮用户消息，形成 `messages` 列表。概念上类似：

```python
{"role": "user", "content": "我想了解用户研究方向"}
```

工程里的对象还可能包含工具协议需要的字段。关键是 `role`、`content` 和列表顺序要保留，较早的历史不能把本轮用户话语覆盖掉。

## 2. 模型提出工具调用

`model` 接收消息列表和 `tool_definitions()` 的工具说明。模型可能返回普通回答，也可能返回一个或多个工具调用。每个工具调用至少有一个名称、参数文本和 `id`。参数文本由 `sanjing.safety.parse_arguments(...)` 解析，再通过权限与字段检查。

模型输出是外部输入：`sanjing.safety.parse_arguments` 先解析调用结构，`check_tool_permission` 和 `validate_schema` 再确认权限及参数。工具名不在 `_TOOL_SPECS` 注册表、字段缺失、类型错误、出现额外字段，都会在业务函数运行前被拒绝。拒绝事件也保存到账本，且不会调用任何任意命令执行器。

## 3. 工具执行并产生账目

`tools.execute_tool(ctx, call)` 负责统一入口：检查工具是否注册，校验参数和会话权限，运行指定业务函数，再把成功或失败写入执行事件。需要保存证据的业务函数会调用 `_save_evidence()`；只注册工具并不会自动定义证据内容。资料检索产生候选证据，匹配函数记录计算输入、规则、贡献和缺失项，提交建议时再列出真正采用的证据 ID。

工具成功返回的字典交给 Agent 主循环。主循环把结果追加到 `messages`，并带回原 `tool_call_id`。这一对消息可以读作：“助手在这个 ID 上提出调用，工具用同一个 ID 回答”。

## 4. 建议和查看依据

只有提交建议的工具通过引用检查后，才会形成可发布的建议记录。检查确认引用 ID 存在、在当前会话范围内，计算事实来自成功执行记录；它不自动判断论文或岗位资料是否真正支持判断。

这里与教材有一处明确不同：`submit_recommendation` 成功后，主循环直接从账本渲染最终回复，不再让模型随意补写另一段结论。普通模型文字被标为未经校验；需要追问时调用 `ask_user`，由程序给出固定问题。

回合结束后，`viewer.write_snapshot(db_path, session_id, turn_id, output_dir)` 调用 `store.snapshot(...)` 取出该轮需要展示的结构化数据，写成使用 `turn_` 加 UUID 的独立 HTML 页面。页面只把数据作为文本显示并做 HTML 转义；工具日志可展开查看。模型原始消息和内部推理不会被页面展示。

## 5. `append` 与 `return` 是两件事

教材第 2 章提醒：`items.append(value)` 会修改传进去的列表，但表达式返回 `None`。因此常见写法是先 `messages.append(tool_result_message)`，再在需要时 `return` 一个结果对象。不要写 `messages = messages.append(...)`，那会让变量变成 `None`。

## 6. 失败时数据怎样走

模型超时、空响应、截断或请求次数达到上限时，整轮保持未完成。工具参数或引用错误会先作为工具结果回传，模型可以在剩余次数内修正；成功修正后仍可完成任务。失败事件保留原有状态，不会被改写为成功。

`model.ask_llm` 使用一个只负责 HTTP 的守护线程，主线程最多等待六十秒。这个边界是为了防止网络持续缓慢传输导致程序一直等；晚到的结果不会执行工具。请求超时不等于服务商停止处理或取消计费，所以程序不自动重试。主循环本身仍是你熟悉的普通 `for` 和 `if`。
